# Phase 3 + 4: getting into a game, and resilience (reviewed design)

Status: design only, reviewed against the code on 2026-10-09 (room.js, index.js, lobby.js, ZbNet.cs, LegacyNetworkShim.cs, ZbNet.jslib, WebGL template, sc_gamecontrol, sc_matchcontroller, sc_spawner, sc_player, sc_zumbi, sc_life, sc_timecontrol, scene list).
Hard rule: gameplay stays exactly v0.7. Everything sits around the game (menus, lobby, transport roles). The few places that would change observable game rules are marked **[v0.7 DEVIATION]** and are off until Vito approves.
Phase 1 (batching, interpolation, stats) is being edited concurrently: new logic goes into NEW files (`ZbMenu.cs`, `ZbSettings.cs`, `ZbSession.cs`, `ZbMigrate.cs`); hooks into existing files are a few lines each; rebase after Phase 1 merges.

## 0. What the review found wrong or missing in the first draft

Each item was checked against the code; evidence in brackets.

1. **Quick Play cannot reuse the `OnFailedToConnect` candidate list.** [`sc_gamecontrol.cs:762-880`: the first statement is `Application.LoadLevel(2)`; scenes are 0 menu, 1 city, 2 empty (`EditorBuildSettings.asset`); in the retry branch it also calls `Network.Connect` directly, and the reload then fires `OnLevelWasLoaded` with `gamestate == 5`, which does `GameObject.Find("scenecontrol").transform` (`:691`), an object that exists only in `city.unity`, so a NullReferenceException and a second Connect.] The list has only ever had one entry in this port, so it is untested. Fix: pick the room BEFORE loading the city (section 2.5); only the single-candidate path is used.
2. **A match does not start by itself.** The host must press Enter (`sc_player.cs:5436-5442` sets `gamestarted = true`; clients see frase[34] until `matchdata.isstarted`). A room listed in "lobby" state can be an abandoned waiting room. Quick Play ranking must use `started`/`ended`/age (2.5), and C_META must report `ended` too (`sc_matchcontroller.cs:611`).
3. **Invite hook belongs in `OnGUI` (first frame, `gamestate == -1`, line 1741), not in `Start()`.** `Start()` ends with `update_manequim()` and `update_gunshow()` that touch scene objects; calling `LoadLevel(1)` from inside it races them. Auto-join also has no user gesture: pointer lock, fullscreen and audio need a click, so show a "Click to play" overlay after the city loads.
4. **Passwords must not ride in the invite URL by default** (history, Referer, chat unfurls). Password rooms open the existing password prompt (state 28). `?pw=` stays supported but is stripped by `replaceState` at once and never logged.
5. **Invite/Quick Play must check the build version.** Rooms are typed `"Zumbiblocks " + buildversion` and the list filters on it. `/api/room/:code` returns `type`; a mismatch shows "This room runs another version" instead of joining.
6. **Publishing `lat/lon` of every host is a privacy leak** (city-level location of a private person in a public JSON). Store them server-side only; publish `colo` and country. Distance is computed in the Worker.
7. **Host on mobile/touch**: the game needs keyboard, mouse and pointer lock, and a 100 MB+ WebGL build; iOS also kills WebSockets of backgrounded pages without a close event. Gate it: on `(pointer: coarse)` devices the template shows "Desktop browser needed" before loading the build, and Create/Quick Play never run there. Section 4 covers the residual (laptop lid close, tab discard).
8. **Reconnect cannot call `StartClient`**: `StartClient -> ResetSession` wipes mode, playerIp, pending RPCs, `ZbSync`, counters and views' session state (`ZbNet.cs` ResetSession). Resume needs a separate `ZbSession.Resume()` that reopens the socket only. Also the resumed WELCOME must NOT run `Notify("OnConnectedToServer")` (`:583`), which would instantiate a second player spawner (`sc_gamecontrol.cs:727`). It must also not fire OnPlayerConnected/Disconnected on the host.
9. **The "seq-exact, exactly-once" resume had holes.**
   - The relay replays the rejoiner's own buffered entries back to it (own `INST` is deduped by `roots`, own buffered RPCs would be applied twice, e.g. `setpermission`, kills, money). Replay must skip `sender == me`.
   - Messages in flight when the socket died are silently lost on both sides. Add cumulative counters: the client counts buffered ops it sent (INST, buffered RPC, DESTROY, REMOVE), the relay counts those it parsed from that player (persisted in the limbo record) and returns the count in the resumed WELCOME; the client re-sends the tail from a ring of its last 256 buffered ops. Count-based, so no duplicates.
   - `loadSnapshot()` renumbers `seq` from 0 (`room.js loadSnapshot`), so a DO restart invalidates every client's `lastSeq`. Persist `seq` per entry in the snapshot (add a format version byte) and persist `this.seq`; also write a snapshot when a player enters limbo. On any mismatch the client is refused with REJECT(10) and rejoins fresh; a blind full replay is never allowed (non-idempotent RPCs).
   - `ZbWsOpen` resets the JS queue; unprocessed frames are dropped. That is safe only because `lastSeq` advances from `S_SEQ` processed in order. Keep that invariant and test it.
10. **Slot and id accounting with limbo.** `fetch()` currently requires `players.has(0)` for any join and counts `players.size >= max` (`room.js`). A host in limbo makes every join answer NOT_FOUND, and a limbo player's slot can be taken by a newcomer so the rejoin hits FULL. Rules: capacity = `players.size + limbo.size`; joins during host limbo get REJECT(9) "host reconnecting, retry"; `nextId` is never reused (already true, MAX_PLAYER_ID 250 stays); lobby `players` counts limbo.
11. **Hidden tabs look like dead sockets.** Pings come from `ZbNet.Tick` every 2 s; a hidden tab does not tick, so a staleness rule ("no frame for 10 s") would put every background-tab client into limbo and then drop its avatar after the grace (today they are never dropped). Staleness must be gated by the JS-sent `C_VIS(hidden)`: hidden players are never limboed (they keep their slot; optional "away" marker); only visible-and-silent sockets are. Also the JS receive queue (`s.queue`) is unbounded while the tab is hidden: cap it (drop oldest unbuffered `S_STATE`/`S_TIME` frames; buffered ones must be kept, so cap by dropping only frames that contain no buffered op, or just warn above 64 MB).
12. **"No in-page trick keeps the host simulating" was asserted, not measured.** `Application.runInBackground = true` is already set (`sc_gamecontrol.cs Start`). What Unity 6 WebGL does in a hidden tab with that flag (rAF stops; some Unity versions fall back to a timer) must be measured by a spike (4.2) before the design commits to "detect and migrate only". Browser timers are clamped to 1 Hz (1/min after 5 min hidden), so the likely result is still "unplayable", but the answer decides whether a cheap 1 Hz "keep alive" mode exists.
13. **Closing a tab on purpose must not enter limbo.** `ZbWsClose` calls `ws.close()` with no code. Use `ws.close(1000, "bye")` for intentional leaves; a tab close or reload produces 1001. Relay: code 1000/1001 means leave now (today's behaviour: immediate `dropPlayer`); 1005/1006/no close frame means limbo. Kick and ban (`R_KICKED`) never create a resume token.
14. **Level C: the successor must also restore client-side host state the draft ignored.** `hostType/roomName/hostComment/hostListed` are empty on a client; the first `SendListing()` would overwrite the relay's room type with `""` (`room.js C_LISTING`) and the room vanishes from the typed list. `remoteCount` must be set from the roster or `SendRpc` skips all unbuffered RPCs ("nobody to tell", `ZbNet.SendRpc`) and zombie animation stops. `playerIp` (also feeds the ban list), `Network.peerType`, `gamecontrol.matchcontroller/matchdata/iamserver/gamestate`, `sc_spawner.matchdata` references. The relay already keeps name/type/pw/listed in `meta`: send them to the successor with the roster.
15. **The draft contradicted itself on spawner registration.** Level C said both "clients re-send `addmyspawner`" and "do not call `addspawner`". `addmyspawner` -> `addspawner` appends and re-issues `setpermission` (`sc_matchcontroller.cs:310`), reshuffling ids. Decision: clients send nothing; the successor fills `everybodyspawners[]` itself by `sc_spawner.myid` (set by `setpermission`, `sc_spawner.cs:234`) and sets `spawners`. The hole of the old host is then removed by the existing null-compaction (`removespawner` swaps the last spawner into the hole and broadcasts `setpermission(mode 2)`, which is the same as a normal disconnect).
16. **The zombie hp fallback was wrong.** Wave scaling is applied at spawn time with the wave of that moment (`sc_matchcontroller.cs:560-575`), so "scale by current wave" mis-scales older zombies. Also client copies are not "prefab hp": shooters apply damage locally and send `hurtme` to Others (`sc_player.cs:3999-4004`), so clients hold unscaled hp minus damage. Without a snapshot the successor keeps the client mirror (unscaled) and logs it; the 1 Hz snapshot is the only correct source.
17. **Owner remap is wider than `isMine`.** Verified: no game script reads `ownerId`; scripts use `NetView().owner`, `isMine`, `Network.player` (e.g. `owner != Network.player` in kick/ban). So remap in three shim places: `NetworkView.isMine`, `NetworkView.owner`, `NetworkViewID.owner/isMine`, via one helper `ZbNet.EffectiveOwner(ownerId)`. Relay side: `ownerOf()` for scene views, `C_ECHO` (`me !== 0`), `C_KICK` (`!== 0`), `C_PING` info routing, S_CONNECTED target, `alarm`, `fetch` all use `meta.hostId` (needed for Level C only, see 3.3).
18. **Level B can be much simpler than the draft** and keep `hostId == 0` forever (3.2): the relay keeps the room code alive, a chosen player starts a fresh host session claiming that code, everyone else reconnects by code through the existing join path. No role pointer, no owner remap, no adopt pass.
19. **Level A is a rule change.** v0.7 punishes clients when the host leaves (`lastaccmoney = 0`, nothing banked, `sc_gamecontrol.cs:703-720`). Banking their money like the ESC "Disconnect" does (`sc_spawner.cs:1261`) is kind, but it is an economy change: **[v0.7 DEVIATION]**, behind a flag, Vito decides. (Abuse check if approved: voluntary disconnect already banks, so no new exploit.)
20. **Rate limiting vs NAT.** Hackathon/office/school NATs put many players on one IP and a Wi-Fi blip makes all of them retry at once. 30 joins/min per IP would 429 them. Separate buckets: new rooms 5/min, first joins 60/min, rejoin (has `rejoin=` param) 120/min, `/api/*` 120/min; 429 on a WS upgrade must be treated by the client as "retry with backoff" while in grace, not as a final failure. Validators (RPC name/args walk, prefab index bound, per-sender caps) ship in shadow mode (count and log, do not drop) for a few sessions first; a false reject would break gameplay silently.
21. **Smaller corrections.** `cache-control: public, max-age=2` does nothing for a Worker response without the Cache API: either use the Cache API or drop it. Reserve op numbers now (Phase 1 uses 9-11, Phase 2 uses text frames): new client ops 16 `C_META`, 17 `C_VIS`, 18 `C_SNAP`, 19 `C_ADOPTED`; server ops from 0x90 up; record them in MULTIPLAYER.md in step 4.1 so concurrent work does not collide on 12-15. `Mouse Y` claim verified: aiming reads it only at `sc_player.cs:2823` (the other two reads at 4701/4708 are camera offsets of another view), so invert Y is one line. `/api/ping/:code` wakes a Room DO per probe: cap to the 8 visible rows, once per list open/refresh, and treat it as "ping via relay path", which is what a player will actually get.

Claims in the first draft that were checked and hold: menu is a `gamestate` machine in `OnGUI` with the quoted states (-1 at 1741, 22 customise at 1943, 24 play at 2346, 26 list at 2409, 27 code at 2558, 28 password at 2384, 25 create at 2596); list label is hard-coded `"/16"` (2537); nick persists as `ZB_<saveversion>_prefname` (default `"player"`), `juststarted` is `ZB_<v>_start`; `def_fov = 70` (`sc_player.cs:338`); `mouse_sense` is copied once at spawn (`sc_spawner.cs:359`); `NetworkView.isMine` is `ownerId == ZbNet.localId`; day clock `asktimer` answers `Network.isServer` at call time; `ZbQuery` / `ZbWs.Query()` exist.

## 1. Facts that shape the design

* Host-only state that is NOT in the relay buffer: `sc_matchcontroller` (wave timers, `longwaveconter`, `increasesecs`, spawn counters, `bannedip[]`, `everybodyspawners[]`), zombie hp and wave scaling (`quantia`, `headlife`, `dmgmin/max`, `walkspeed`, `carryitem`, `killerid`, AI state), ground-item quantities (`sc_canbetaken.quant/ammo/decay`), supply/crates, construction durability (unaudited), vehicles (unaudited). Mirrored on every peer: wave/time/started in `matchdata`, positions, buffered instantiates/RPCs, players (client-owned).
* Scripts that choose their role in `Start()` and will not re-evaluate on promotion: `sc_zumbi` (`!isMine` disables), `sc_findmyarea` (`!Network.isServer` disables, `:15`), `sc_barbwire`, `sc_beartrap`, `sc_landmine`, `sc_lootdroper`, `sc_suplly`, `sc_timedkillme`, `sc_terraanim`, `sc_ammocrate`, `sc_ammo`, plus the `sc_updateposition`/`sc_sendpositionupdate` pair. This is the adopt table for Level C and it must be generated by a script (grep for `Network.isServer|isClient|isMine` inside `Start/Awake/OnEnable`) and re-run on every game-script change.
* Sockets: the relay today has no staleness check (host or client silence never closes a room); `webSocketClose` receives the close code.

## 2. Phase 3: getting into a game

### 2.1 Settings (`ZbSettings.cs`, `ZbMenu.cs`)
* Keys `ZBX_fov` (default 70, 60..110), `ZBX_invy` (0), `ZBX_quality` (default = today's look), independent of `saveversion` so version bumps do not wipe them. Sensitivity and volume reuse `_sense` / `_sound` and mirror into `gamecontrol.mousesense/audiovol`. `PlayerPrefs.Save()` after every change (WebGL flushes IndexedDB only on Save).
* UI: new `gamestate 33`, reached from a new "All settings" row in Options (state 9, line 2977; add one `newhud[0]` row, shift Back 50 px). In-game: ESC panel of `sc_spawner` gets a "Settings" button that sets `ZbMenu.overlay`, drawn from `NetRunner.OnGUI`.
* Live apply: `ZbSettings.Tick()` 2 Hz finds the local `sc_player` (`NetView().isMine`) and sets `mouse_sense`, `def_fov` (and `camcript.to_fov` when not zooming). Zoom uses `def_fov - gun.add_fov`, so it keeps working.
* Invert Y: replace the one read at `sc_player.cs:2823` with `ZbSettings.MouseY()`.
* Quality presets: start with plain Unity APIs (AA, `masterTextureLimit`, terrain pixel error, lightmaps via `turnoff_LM`). Render scale is a separate spike (the template pins `devicePixelRatio: 1`; whether Unity 6 honours a runtime backing-size change is unknown). Defaults reproduce v0.7.
* Acceptance: values persist across reload; untouched profile is identical to v0.7; zoom still narrows by `add_fov`.

### 2.2 First-run nickname
* New `gamestate 30`. Hook at line 1741: `if (gamestate == -1) gamestate = ZbMenu.EntryState(this);` where EntryState returns 30 if `ZBX_nick_ok != 1` and (`juststarted == 0` or nick is the default `"player"`), 32 if an invite/quick link is pending, else 0. Existing players with a real nick are not asked.
* Sanitiser (`ZbMenu.CleanNick`): trim, collapse spaces, strip control chars and bidi overrides, allow letters/digits/space/`_-.`, 2..10 chars, not `player`. Applied in state 30 and after the field in state 22.
* Duplicate nicknames: allowed, as in v0.7. Nothing keys on names (kick/ban use the player index, `sc_spawner.cs:475-488`; bans use the room-scoped ip id). No uniqueness rule, no suffixing (it would need a rename RPC and would differ from v0.7).
* Room names built from nicks (`nick's game`) go through the relay-side listing sanitiser (4.0).

### 2.3 Server info APIs and C_META
* `GET /api/room/:code` -> `{exists, name, type, players(incl. limbo), max, pw, started, ended, wave, hostState}` or 404 `{exists:false}`. Never returns the password or any address. Implemented as a Room DO RPC method `info()` that must not create storage for a non-existent room; junk codes still instantiate a DO stub, so it is behind the rate limit (4.0) and a cheap regex gate.
* `/api/rooms` rows gain `wave, started, ended, age, colo, country, v`. No lat/lon.
* `C_META` (op 16, host only): `u16 wave, u8 flags(1 started, 2 ended), u8 alive`. Sent by a tiny host poller in `ZbMenu` reading `sc_matchcontroller` public fields every 2 s, only on change. Old hosts never send it: columns show "-". Relay stores in `meta`, forwards via `lobbyUpdate()`.
* `GET /api/ping/:code` -> `stub.ping()`; client measures `fetch` RTT with `performance.now()` (2 samples, min), for at most 8 rows per list open/refresh, cached 10 s.

### 2.4 Richer server list
* Hooks in state 26: header call after the existing header labels (~2480-2500), `ZbMenu.ListRow(...)` after the `/16` label (2537), and replace `"/16"` with `"/" + playerLimit`. Free space between name column (x 675) and the players column fits Wave, Ping, Region. Sort in `FetchRooms` (full last, then ping, then players); `server_select` indexes `hostData`, so sort before building the array. Full or version-mismatched rooms are greyed and not joinable. Auto-refresh every 10 s while open (a second `RequestHostList` while a request is pending is already superseded by `listRequest`).

### 2.5 Quick Play (client-side, no retry list)
* New first row in state 24 (line 2346; one more `newhud[0]` row, other rows +50 px). New transient `gamestate 31` "Finding a game..." with Cancel.
* Flow in `ZbMenu.QuickPlay`: `GET /api/quickplay?type=<"Zumbiblocks "+buildversion>` returns up to 3 candidates already filtered by: same type, `!pw`, listed, `players + limbo < max`, `!ended`, host not away. Ranking: started rooms with 1..max-2 players first (they need people), then not-started rooms younger than 3 min with >= 1 player, then by distance (server-side from `request.cf`), then newest. The CLIENT then re-checks the first candidate with `/api/room/:code` immediately before connecting (closes the race), and walks the candidate list in `ZbMenu` BEFORE `LoadLevel(1)`. Only one candidate is ever handed to `gamestate = 5` / `ipstotry = 1`. If the connect still fails (room filled in between), `OnFailedToConnect` is hooked at its first line: `if (ZbMenu.QuickFail(this, error)) return;` which re-runs Quick Play once, then creates a room.
* No candidate: create exactly as state 25 does (`InitializeServer(16,...)`, `RegisterHost(type, nick + "'s game", "Quick Play")`, `gamestate = 3`, `LoadLevel(1)`), listed by default.
* Quick-created rooms start like any room (host presses Enter). **[v0.7 DEVIATION, optional]** auto-start a 10 s countdown when the first other player joins a Quick-Play-created room; off by default, Vito decides. Without it, the joiner sees the existing "waiting for host" text.
* Acceptance: empty server creates a listed room; second browser's Quick Play joins it; full/ended/passworded rooms are never offered; two simultaneous Quick Plays do not both create separate rooms forever (second one joins the first within a retry).

### 2.6 Invite links `?room=CODE`
* Page: parse `room` (and `pw`) before the build loads; banner "Joining room CODE...". On touch devices show the desktop-only notice instead of loading. DOM bar "Room ABCDE [Copy invite link] [Share]" shown when Unity calls `ZbSetRoomUi(code, hosting)`; copy runs from a real DOM click (`navigator.clipboard.writeText`, `execCommand` fallback; `navigator.share` on mobile). `beforeunload` confirm only while hosting with others present.
* Unity: `ZbMenu.EntryState` returns 32 when the query has `room`. State 32 (first `OnGUI` frame): nick first if needed (30), then `GET /api/room/CODE`. Outcomes: 404 -> state 27 with "Room not found or closed"; `pw` -> state 28; full -> "Room is full"; type mismatch -> "This room runs another version"; `hostState` away -> "Host is reconnecting, retry in a few seconds"; ok -> set `ipstoconec = {CODE}; ipstotry = 1; trynow = 0; iamserver = false; gamestate = 5; LoadLevel(1)` exactly like the button at line 2558. After the city loads show "Click to play".
* `ZbClearInviteParam()` removes `room`/`pw` with `history.replaceState` once consumed, so a refresh after leaving does not auto-rejoin. Failure after the pre-check (race) falls back to the normal OnFailedToConnect text; reject reasons 9/10 get distinct texts through one patch line (`ZbMenu.PatchError(this)` at the end of the error branch), since today everything maps to "Room not found or closed".
* Two tabs of the same browser both with the invite: second gets a normal separate player; no special handling.

## 3. Phase 4: resilience

### 3.1 Protocol v3 (append-only; v2 sockets keep today's behaviour byte for byte)
`PROTO` accepted: 2 and 3. A v2 socket never receives a v3 message, gets no grace and its host leaving closes the room (already-open tabs survive a deploy). Regression test for v2 is mandatory.

Client -> relay: `16 C_META`, `17 C_VIS {u8 visible, u8 fps, u16 rttMs}` (also written by the JS bridge itself on `visibilitychange`/`pagehide`, as a complete `u16 len + body` frame straight onto the open socket, because Unity does not tick in a hidden tab), `18 C_SNAP {u8 snapId, u8 part, u8 total, bytes}` (host, 6 KB chunks), `19 C_ADOPTED`.
Relay -> client: WELCOME extended with `str8 token, u8 graceSec, u8 epoch, u8 flags(1 resumed, 2 restart-claim), i32 hostId, u32 acceptedBufferedOps` (old readers ignore trailing bytes); `0x8E S_SEQ u32` (appended at the end of any frame containing buffered entries); `0x8F S_HOST_STATE {state, secondsLeft}`; `0x90 S_HOST_CHANGE {i32 newHost, i32 oldHost, u8 epoch, u8 mode(0 migrate, 1 restart)}`; `0x91 S_HOST_SNAP`; `0x92 S_ROSTER` (+room meta); `0x93 S_PLAYER_STATE`; `0x94 S_ROOM_READY`; new REJECT reasons 8 replaced, 9 host away, 10 grace expired / bad token / not resumable.
Reconnect URL: `/ws/room/CODE?v=3&rejoin=ID.TOKEN&seq=N&pw=...` (host uses the same route). Token: 16 random bytes per player, stored only in the limbo record and sessionStorage, never logged, single use per socket, invalid after kick/ban/leave/grace.

### 3.2 Relay behaviour
1. **Leave vs drop** by close code (finding 13). Intentional leave: today's `dropPlayer`. Drop: limbo `{token, since, bufOpsAccepted, lastSeq}` persisted to `ctx.storage` (hibernation safe). Host is not told yet.
2. **Staleness** (visible and silent only): alarm cadence `min(heartbeat 5 s, next limbo expiry, host grace expiry)`; a visible player (last C_VIS visible or no C_VIS ever) with no frame for 10 s enters limbo. Hidden players never do.
3. **Grace**: clients 20 s, host 15 s (open question 2). On expiry: `dropPlayer` (S_DISCONNECTED to host, avatar destroyed by the game's existing handler).
4. **Resume**: validate token and `bufGen`; replay buffered entries with `seq > clientSeq` and `sender != me`, plus tombstones (`tomb` ring, 60 s) as `S_DESTROY`, then `S_SYNC_DONE`. Client re-sends its unacked tail by count. Capacity, joins and lobby count include limbo.
5. **Host-bound queue** while the host is away/stalled/migrating: mode-0 RPCs queue in `pendingToHost` (300 entries / 128 KB, oldest dropped; echo/ping-info are not queued), flushed on host return or `C_ADOPTED`.
6. **Host absent policy**: socket gone -> `S_HOST_STATE(away, 15)`, joins get REJECT(9); host back inside grace -> resume. Host hidden (C_VIS) -> `S_HOST_STATE(hidden, 30)`, cleared on visible. Grace over -> Level B (default) or C (flag).
7. **Fencing**: `epoch` per host term; frames from a socket that is no longer host are dropped and the socket gets REJECT(8). A returning hidden host can never cause split brain.
8. Existing buffer, compaction, `C_STATE` fan-out, `S_TIME` stamping untouched.

### 3.3 Levels of "host left" (ship in this order; each degrades to the previous)
* **Level A** (client only) **[v0.7 DEVIATION, flag]**: on host loss with grace expired, bank the match money like ESC-disconnect does and show the end screen "Host left" (state 12) instead of "lost connection". Off by default until approved. Without the flag the behaviour is v0.7.
* **Level B, "claim restart"** (hostId stays 0): relay picks a successor (visible, lowest reported rtt, lowest id; never a limbo player; if none, wait the grace then close). It sends the successor `S_HOST_CHANGE(mode 1)` with a one-time claim token and everyone else a "host changing, hold on" state. Each client first banks money if Level A is on. The successor runs the normal host start (`gamestate = 3`, `InitializeServer`, `LoadLevel(1)`) but connects to `/ws/host?claim=CODE.TOKEN`; the relay validates, resets the buffer/epoch, makes the new socket player 0 and sends `S_ROOM_READY` to the others, who reconnect by code through the unchanged join path (new ids, fresh avatars, inventory is client-side and kept). Room code, password, name, listing and ban list (ip ids are per code+ip, stable) survive. Match restarts at wave 1. If the claim does not arrive in 10 s the next candidate is tried; after 3 failures the room closes. No role pointer, no owner remap, no adopt pass; it reuses tested code paths and is the production behaviour until C is proven. The tab must not run `ResetSession`-style teardown twice: successor calls `Network.Disconnect` first, exactly like leaving a match.
* **Level C, state-preserving migration** (`?migrate=1`, relay `meta.hostId` pointer, epoch fencing, owner remap per finding 17, `ZbMigrate.cs`). Successor sequence:
  1. Restore client-side host state (finding 14): `mode = Host`, `peerType = Server`, `remoteCount`, `playerIp`, listing fields from S_ROSTER meta, `gamecontrol.iamserver/gamestate = 3`, references.
  2. Destroy the old host's player-ish roots (owner 0 with `sc_spawner`, `sc_player`, `sc_shot`, `SC_MISSILE`, `sc_granada`, gun objects) with `C_DESTROY` one by one. Never blanket `DestroyPlayerObjects(0)`/`RemoveRPCs(0)`: zombies, matchdata and items share that owner id.
  3. Rebuild `sc_matchcontroller` (instantiate prefab, set `matchdata`, `myspawner`, `gamecontrol`, wave/minute/second/`gamestarted`/timers/`bannedip` from the snapshot, fallback to matchdata mirror), fill `everybodyspawners[myid]` from local spawners (finding 15), `matchdata.senddata = true`.
  4. Adopt pass (table from section 1; generated list, per-object try/catch, per-type counters in `ZBMIGRATE {...}` log). Zombies: enable `sc_zumbi`, disable `sc_zumbionlinecontroller`, `isKinematic = false`, set `gamecontrol/matchcontrol`, apply snapshot hp/scaling, `state = 0` if older than 4 s, remove their `ZbInterp`. `sc_findmyarea` on ALL player objects. Items/traps/supply per section 1. Constructions and vehicles: owner remap only until audited.
  5. `C_ADOPTED`; relay flushes `pendingToHost`.
  Everyone else on `S_HOST_CHANGE`: `hostId`, `epoch`, reset interpolation clock for the new sender, banner "<nick> is now host". Snapshot (`ZbMigrate.SnapshotTick`, 1 Hz, host only, reads public fields, no script edits): header + per zombie `(view, quantia, headlife, walkspeed, dmgmin, dmgmax, flags)` + per ground item `(view, quant, ammo, decaytime)`, about 3-4 KB at 50 zombies, chunked below the 60 KB frame cap, lowest priority, newest complete one kept in memory and storage (16 KB cap).
  Failure ladder: no snapshot -> mirror only, logged; adopt exception -> continue; successor leaves or no `C_ADOPTED` in 8 s -> next candidate, epoch++, and the failed successor does a hard rejoin as a client (it may already have enabled host scripts, so it must not keep playing as it is); more than 20 s -> Level B.
  Unavoidable losses (documented): old host's avatar and in-flight projectiles; zombie AI micro-state (re-acquired in about 1 s); up to 1 s of hp/damage regression; unbuffered RPCs during the gap.
  Phase 1/2 composition: batching carries C_VIS/C_SNAP and the reconnect outbox through `Queue()`/`FlushOut()` (the outbox is the unflushed `outBuf` plus a 256-op ring); `ZbInterp.Feed` keys on view + sender clock so reset `Clock(newHost)`; the WebRTC lane (Phase 2) is torn down on S_HOST_CHANGE/REJECT and renegotiated with the new host over the WS control path; keep `hostId` out of RTC state.

### 3.4 Client side
* `ZbSession.cs` owns lifecycle: `Offline, Connecting, Online, Reconnecting, HostAway, Migrating`. Hooks: `OnSocketClosed` (only when `Connected && graceSec > 0 && !userLeft && reason not kicked/room closed`) -> `BeginReconnect()`; `ProcessMessage` cases for the new ops; `Queue()` drops ephemeral ops while reconnecting and keeps buffered ones in a capped outbox (256 KB); backoff 0.4, 0.8, 1.6, 3, 3 ... until grace; then the existing `OnDisconnectedFromServer` path (v0.7 behaviour). `S_INST` dedupes by `roots.ContainsKey`. Overlay from `NetRunner.OnGUI`: "Connection lost, reconnecting 14 s", host-away banners, optional "<nick> reconnecting".
* Scope: network drops only. A page reload loses the Unity world and joins fresh via the invite link (avatar is not re-adopted).
* Hidden host (after spike 4.2): at minimum the template warns the host (banner + title blink), JS sends `C_VIS`, clients see "Host's tab is in the background" with a countdown, then B/C. A silent-audio keep-alive is not used.

## 4. Edge cases and decisions

| Case | Behaviour |
|---|---|
| Room full (create/quick/invite) | List/`/api/room` count limbo; Quick Play never offers full rooms; direct join gets R_FULL "Server is full"; invite pre-check says "Room is full" before the city loads. Rejoin always has its slot (reserved while in limbo). |
| Host on mobile/touch | Desktop-only gate in the template, before the build downloads; no Create/Quick Play. Laptop lid close / tab discard of a desktop host is the hidden/away path (3.2.6). |
| Duplicate nicknames | Allowed (v0.7); nothing keys on names. |
| Invite to a closed/never-existing room | `/api/room` 404 -> state 27 "Room not found or closed", no city load. Race after the pre-check -> normal OnFailedToConnect text. Invite param is cleared so refresh does not loop. |
| Invite to a password room | Password prompt (state 28); `?pw=` supported but stripped and never logged. |
| Invite to a started/ended match | Joining a started match is allowed (v0.7). Ended: "This match has ended", offer Quick Play. |
| Invite from another build | Type mismatch message, no join. |
| Reconnect while host migrating | WELCOME carries `hostId/epoch` so the client sets the new host before replay; it does not need S_HOST_CHANGE. In Level B the old ids are gone: reconnecting by token yields REJECT(10), the client auto-joins fresh by code after S_ROOM_READY. |
| Old host returns after takeover | REJECT(8) "someone else took over", offered "Join as player" (fresh join, new id). |
| Successor dies mid-migration | Next candidate, epoch++; demoted successor hard-rejoins. All candidates limbo: wait the grace, then close. |
| Kicked or banned player | No token is minted; kick closes with R_KICKED, no resume. Ban list is carried in the snapshot (C) or relay-kept ip ids (B). |
| NAT / many players, one IP | Separate rate buckets (finding 20); ip-id ban hits all players behind that NAT (existing behaviour, document). |
| Intentional close/reload | Immediate leave, no limbo (close code). |
| DO restart / deploy mid-match | Persisted seq + `bufGen`; mismatch -> REJECT(10), fresh join. v2 tabs unaffected. |
| Host changes password via chat command | Existing gap: `Network.incomingPassword` is only read at `StartHost`, the relay's `pw` never updates. Out of scope, noted. |

## 6. Test strategy
* Relay (`server/test/relay.test.mjs`): `/api/room`, quickplay ordering and filters, C_META validation, ping; rejoin within/after grace; wrong/used token; no double delivery; own-entry skip; tail resend by count; tombstone replay; DO-restart mismatch -> REJECT(10); capacity with limbo; host-bound queue order/caps; claim flow; promote selection and epoch fencing; v2 sockets unaffected; shadow validator counters.
* E2E (`server/test/e2e`): nick prompt on fresh profile, invite join (ok/closed/full/password/version), Quick Play (empty, joinable, full, simultaneous), settings persistence, client drop 3 s/25 s, host drop 5 s/25 s, hide host, host quits with 3 players (A/B/C by flag). Run each under `?netsim=120,30`. Assertions use `DebugDump`, `ZBSTATS`, `ZBMIGRATE`; allow only the known `asktheanimation` NRE.
* Soak: 30 min, 4 browsers, random client drops every 2 min, a host swap every 5 min, compare zombie counts to baseline.
* Gameplay parity: with new features unused, a recorded session matches v0.7 (`?legacy=1` plus the existing measure scripts).

## 8. Residual risks
* Level C correctness depends on a complete adopt table and on unaudited vehicle/construction authority; only the multi-browser test proves it. B is the automatic fallback.
* Zombie AI micro-state and up to 1 s of hp regression are lost on migration (only at the moment a host leaves, where today the room dies).
* A hidden host cannot be kept simulating if the step-10 spike confirms rAF/timer throttling; the design then detects, warns, and migrates.
* Resume correctness rests on the three invariants in finding 9 (skip own entries, count-based resend, in-order `S_SEQ`); they need the targeted relay tests before the feature ships.
* Phase 1 edits to `ZbNet.cs`, `room.js`, the jslib may conflict with the hooks (`Queue`, `OnSocketClosed`, `ProcessMessage`, WELCOME). Mitigation: new files, tiny hooks, rebase after Phase 1.
* The one-line hooks in decompiled `sc_gamecontrol`/`sc_player`/`sc_spawner` (about 8) would be overwritten by a future re-rip; the Unity project is the source of truth, record them in RECOVERY.md.
* Clipboard from the IMGUI canvas is unreliable on Safari (so the copy button is DOM), mobile share needs manual checks.
