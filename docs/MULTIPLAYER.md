# Online multiplayer

The original game used Unity's legacy networking (RakNet): one player ran the authoritative "server", the others
connected to it, and a master server listed open games. This revival keeps that model. One player's browser is the
host; a Cloudflare Worker + Durable Object relays messages between the browsers over WebSockets and keeps the room list.

```
 browser A (host)            Cloudflare                          browser B, C ...
 Unity WebGL                 Worker  ──  Lobby DO (room list)    Unity WebGL
   LegacyNetworkShim  ──WS──▶ /ws/host ─▶ Room DO (relay) ◀─WS──  LegacyNetworkShim
   ZbNet (transport)          /ws/room/CODE                       ZbNet (transport)
   (runs the match)           /api/rooms                          (clients)
```

The game's 319 `networkView.RPC` calls, 36 `Network.Instantiate` calls and the connect/disconnect callbacks are unchanged.
`game/Assets/Scripts/LegacyNetworkShim.cs` re-creates the old API, `game/Assets/Scripts/ZbNet.cs` is the transport,
`game/Assets/Plugins/WebGL/ZbNet.jslib` is the browser WebSocket bridge, and `server/` is the Worker.

## How the game maps onto the relay

| Legacy call | Behaviour now |
|---|---|
| `Network.InitializeServer(1, ...)` | Single player: offline loopback, no network at all (same as before). |
| `Network.InitializeServer(n > 1, ...)` | Opens a room: `GET /ws/host`. The relay answers with a 5 character room code and player id 0 (host). `Network.incomingPassword` becomes the room password. |
| `MasterServer.RegisterHost(type, name, comment)` | Lists the room in the lobby (`LISTING` message). Without it the room is private (join by code only). The menu toggle "Show in server list" decides this; the original default is unlisted. |
| `MasterServer.RequestHostList(type)` / `PollHostList()` | `GET /api/rooms`, filtered to the same `type` string (`"Zumbiblocks " + buildversion`), so different builds do not see each other. `HostData.ip[0]` is the room code, `port` is 0. |
| `Network.Connect(ip, port, password)` | `ip` is the room code (the menu's IP text field, label changed to "Room code"; the list passes it too). Opens `GET /ws/room/CODE`. |
| `OnConnectedToServer` | Fired when the relay's `WELCOME` arrives; buffered state is replayed on the following frames (like RakNet). |
| `OnFailedToConnect` | Room not found / closed (`ConnectionFailed`, message patched to "Room not found or closed"), wrong password (`InvalidPassword`), room full (`TooManyConnectedPlayers`), protocol mismatch. |
| `OnPlayerConnected` / `OnPlayerDisconnected` | Host only, from the relay. `NetworkPlayer.ipAddress` is an anonymous per room id of the connection (hash of IP + room code), so the game's IP ban list works within a session without exposing IPs. |
| `OnDisconnectedFromServer` | Host left / kicked / connection lost; also fired after a local `Network.Disconnect` (host and client), one frame later, like RakNet. |
| `networkView.RPC(name, mode, args)` | See "RPC routing". |
| `Network.Instantiate(prefab, pos, rot, group)` | See "Instantiate". |
| `Network.Destroy(viewID / go)` | Destroys locally and on every peer; drops the object's buffered history. |
| `Network.RemoveRPCs(player)` / `DestroyPlayerObjects(player)` | Executed by the relay (host may do it for anyone, others only for themselves). |
| `Network.CloseConnection(player, ...)` | Host kicks a player (`KICK`). |
| `Network.GetAveragePing(player)` | Each client pings the relay every 2 s and reports its RTT; the relay forwards it to the host. |

### Identity: views, owners, players
* Player ids: host = 0, joiners get 1, 2, 3, ... in order, never reused within a room. `Network.player` is the local id.
* View id (64 bit): for `Network.Instantiate`d objects `(owner + 1) * 2^40 + counter * 2^12 + sub`. `owner` is the instantiating player, `counter` is per player, `sub` (0 for the root, a hash of the relative path for child objects that call `NetView()`).
  For objects that exist in the scene (not network-instantiated) `2^51 + FNV1a(hierarchy path)`; their owner is the host. Both sides load the same scene, so the ids agree.
* `NetworkView` components are added lazily by `NetView()` (the exported prefabs lost their NetworkView components), plus eagerly for every GameObject that has an `[RPC]` method, so incoming RPCs always find a target. `isMine` = owner is the local player.
* Prefabs are identified by index into `Assets/Resources/ZbNetPrefabs.asset` (all prefabs, regenerated by `BuildWebGL`). Same build on every peer, same table.

### RPC routing
`RPCMode` is honoured as in Unity:

| Mode | Local call | Sent to |
|---|---|---|
| `Server` (0) | only if this peer is the host | host only |
| `Others` (1) | no | every other player |
| `All` (2) | yes | every other player |
| `OthersBuffered` (5) | no | every other player, stored for late joiners |
| `AllBuffered` (6) | yes | every other player, stored for late joiners |

* The method is called on every component of the target GameObject that has an `[RPC]` method of that name and argument count (falls back to the first plain match if the decompiled code lost the attribute).
* Supported argument types: `int`, `float`, `bool`, `string`, `Vector3`, `Quaternion`, `int[]` (plus numeric conversions). Anything else is logged and sent as null.
* RPCs that arrive for a scene object whose view does not exist yet are retried for up to 10 s (a scene rescan runs every 250 ms meanwhile).
* The host does not send unbuffered RPCs while nobody else is connected.

### Instantiate
The instantiating peer creates the object locally (with the new view id/owner already known while `Awake` runs) and sends `INST` to the relay.
The relay stores it in the room buffer (`Network.Instantiate` is always buffered in Unity) and forwards it to the others, who instantiate the same prefab at the same pose with the same view id.
A late joiner receives the whole buffer in order: instantiates and buffered RPCs.

The relay compacts the buffer so it does not grow forever (the original relied on RakNet doing similar bookkeeping):
* a buffered `killmebuffered` RPC (what the game sends when a temporary object dies: bullets, particles, sounds...) removes that object's instantiate and all its buffered RPCs, and is still forwarded to the other peers;
* a `killmebuffered` for an object that is already gone is swallowed (every peer's `OnDestroy` re-sends it, which would otherwise be an N^2 echo storm);
* `Network.Destroy` removes the object's history and tells the others;
* `DestroyPlayerObjects(p)` destroys every live object owned by `p` on all peers and removes their history;
* `RemoveRPCs(p)` removes buffered RPCs sent by `p`.

## Wire protocol (version 3; version 2 sockets are still accepted and behave exactly as before phase 4)

One binary WebSocket per player. All integers little endian. A WebSocket message is a *frame*: a sequence of messages, each `u16 length` + body (`body[0]` is the opcode). The client sends everything produced in one game frame as one WebSocket message (split below 60 KB); the relay answers per recipient the same way.

Connect URLs (query values URL-encoded, `v` must be 2 or 3 or the relay rejects with reason 7; phase 4 additions: `rejoin=ID.TOKEN&seq=N` (resume), `stale=ID.TOKEN` (free the slot a crashed tab left in limbo), `claim=CODE.ID.TOKEN` on `/ws/host` (claim restart); version 2 added the messages marked below, a page from the version 1 era is refused instead of misbehaving):

* host: `GET /ws/host?v=2&max=16&name=NAME&pw=PASSWORD&type=TYPE` (the Worker picks an unused 5 char code, alphabet without I, O, 0, 1)
* join: `GET /ws/room/CODE?v=2&pw=PASSWORD` (case insensitive)

Client to relay:

| op | name | body after opcode |
|---|---|---|
| 1 | RPC | `u8 mode, i64 view, u8 nameLen, name utf8, args` |
| 2 | INST | `u8 group, i64 view, u16 prefabIndex, 3 x f32 position, 4 x f32 rotation(xyzw)` (40 bytes total) |
| 3 | DESTROY | `i64 view` |
| 4 | REMOVE_RPCS | `i32 player` |
| 5 | DESTROY_PLAYER_OBJECTS | `i32 player` |
| 6 | KICK (host only) | `i32 player` |
| 7 | PING | `u32 clientTimeMs, u16 lastRttMs` |
| 8 | LISTING (host only) | `u8 listed, str8 name, str8 comment, str8 type` |
| 9 | TIME (v2) | `u32 clockMs`: the sender's `performance.now()`, first message of every frame |
| 10 | ECHO (v2) | `u8 type (0 ping, 1 pong), i32 target, u32 t`: end to end ping, clients may only target the host |
| 11 | STATE (v2) | compact position update, see "State messages" |
| 16 | META (phase 3, host only) | `u16 wave, u8 flags (1 started, 2 ended), u8 alive, [u8 countdown]`: feeds the server list and the Quick Play auto start. 5 or 6 bytes, anything else is ignored. Ops 12-15 are reserved (phase 1/2). |
| 17 | VIS (phase 4, protocol 3) | `u8 visible, u8 fps, u16 rtt`: written by the page itself (jslib) on `visibilitychange`, as a complete frame, because the game does not run in a hidden tab. 18 `C_SNAP` and 19 `C_ADOPTED` stay reserved for host migration level C (not built). |
| 20 | SCORE (phase 5, host only) | `u8 rules (1 Timed waves, 2 More loot), u16 wave, u8 n, n x (u16 kills, str8 name)`: every player's kills for the leaderboard; sent on each new wave, every 15 s and when the match ends (before the META that ends it). Kept in memory, recorded once per match, see docs/LEADERBOARD.md. |

Relay to client:

| op | name | body after opcode |
|---|---|---|
| 0x81 | WELCOME | `i32 yourId, u8 isHost, u8 maxPlayers, str8 roomCode`; protocol 3 appends `str8 token, u8 graceSec, u8 epoch, u8 flags (1 resumed, 2 restart claim), i32 hostId (always 0), u32 acceptedBufferedOps (0xffffffff unknown)` |
| 0x82 | RPC | `i32 senderId` then the client RPC body (`mode, view, name, args`) |
| 0x83 | INST | `i32 senderId` then the client INST body |
| 0x84 | DESTROY | `i64 view` |
| 0x85 | PLAYER_CONNECTED (host) | `i32 id, str8 anonymousIpId` |
| 0x86 | PLAYER_DISCONNECTED (host) | `i32 id` |
| 0x87 | REJECT | `u8 reason`: 1 room not found, 2 wrong password, 3 room full, 4 host left, 5 kicked, 6 rate limited (retry later), 7 protocol mismatch, 8 someone else already claimed the room, 9 host away / restarting (retry), 10 resume refused (token unknown / grace over / bad seq). The relay closes the socket after it. |
| 0x88 | PONG | `u32 clientTimeMs` |
| 0x89 | PING_INFO (host) | `i32 id, u16 rttMs` |
| 0x8A | SYNC_DONE | end of the buffered replay for a new joiner |
| 0x8B | TIME (v2) | `i32 senderId, u32 clockMs`: first message of every frame that came from a peer's frame with a TIME message (not in buffer replays) |
| 0x8C | ECHO (v2) | `i32 senderId, u8 type, u32 t` |
| 0x8D | STATE (v2) | same body as the client's STATE message |
| 0x8e | SEQ (phase 4) | `u32 seq`: newest buffered entry in this frame / replay; appended at the end of every frame that carries buffered entries to a protocol 3 peer. The client keeps the last one it processed (what a resume continues from). |
| 0x8f | HOST_STATE (phase 4) | `u8 state (0 ok, 1 host connection lost, 2 host tab hidden, 3 host left: new match being set up), u8 secondsLeft`. 0x90-0x94 are reserved (host change / snapshot / roster of level C), unused. |
| 0x95 | COUNTDOWN (phase 3) | `u8 seconds` left until the Quick Play room starts by itself (0 = cancelled / started). Sent to everybody except the host, once a second while the countdown runs. 0x8E-0x94 are reserved (phase 4). |
| 0x96 | RESULT (phase 5) | `u8 board (0 solo, 1 team, 255 not ranked), u16 rankToday, u16 rankAllTime` (best-wave board): sent to everybody still connected once the relay recorded the match. |

`str8` = `u8 length` + utf8. `args` = `u8 count`, then per argument `u8 tag` + value: 0 null, 1 `i32`, 2 `f32`, 3 `u8` bool, 4 string (`u16 length` + utf8), 5 Vector3 (3 x f32), 6 Quaternion (4 x f32), 7 int[] (`u16 count` + i32s). The relay never looks inside `args`.

## Feel layer (protocol 2)

Everything here sits between the transport and the game's RPC methods; the gameplay scripts are untouched. Baseline and results are at the end of this section.

### How the original synced positions
There is no `OnSerializeNetworkView` (the exported prefabs have no state-synchronised NetworkView). Positions are plain unbuffered RPCs to `Others`, sent by the owner at a nominal 10 Hz (`sendrate = 10`, counter `+= 1000 * sendrate * dt`, reset to 0 after sending, so 8 to 10 per second at 60 fps and exactly one per frame below 10 fps):

| RPC | sender | args |
|---|---|---|
| `setposstuff` | each player, for its own avatar (`sc_player`) | yaw (int degrees), head angle (int), position, `exposi`, `exposiback`, lean |
| `setzumbistuff` | the host, for every zombie (`sc_zumbi`) | yaw (int degrees), position |
| `updateposition` | whoever owns the object (bags, dropped items, grenades, supplies: `sc_sendpositionupdate`) | position |

The receivers (`sc_onlinecontroller`, `sc_zumbionlinecontroller`, `sc_updateposition`) only store the latest target and chase it every frame (`Translate((target - position) * dt * 10)`, yaw lerp for players, hard yaw set for zombies): an exponential smoothing with a 100 ms time constant on top of 8 to 10 Hz data with the network jitter in it. Visible effects: a lag of 150 to 250 ms behind the sender, and velocity that jumps at every update (stop-and-go) when packets arrive unevenly.

### Host timestamps and clock offset
Every frame a peer sends starts with `TIME` (its `performance.now()` in ms). The relay puts it in front of the messages it forwards to each recipient (`0x8B` with the sender id). The receiver keeps, per sender, the smallest `arrival - stamp` of the last 8 s as the clock offset (the path without queueing; it follows changes by at most 1 to 2 ms per frame, so there are no time jumps) and an RFC 3550 style interarrival jitter of the transit time. Arrival times are taken in the jslib when the browser delivers the frame, not when Unity gets around to reading it. Messages without a stamp (buffer replays) are stamped with arrival minus offset.

### Interpolation (`ZbInterp` in ZbNetSync.cs)
Added automatically to every remote object that receives `setposstuff` / `setzumbistuff` (`ZbSync.TryFeed`, called from `ZbNet.DeliverRpc` for plain RPCs and for compact STATE messages alike).
* Buffer of the last 24 snapshots `(sender time, position, yaw)`.
* Render time = `now - clockOffset - delay`. The delay is adaptive: `max(100 ms, 1.1 * snapshot interval + 3 * jitter + 8 ms)`, at most 350 ms, raised quickly and lowered slowly, and it never changes render speed by more than 20 %.
* Between two snapshots: linear position, `LerpAngle` yaw. Past the newest snapshot: extrapolate with the last velocity for at most 100 ms, then hold. Before the oldest: hold.
* A jump of more than 6 m between two snapshots (spawn, teleport, respawn) clears the buffer and snaps.
* It runs in `LateUpdate` with execution order -50, writes the pose into the transform and into the controller's own target fields (`posissao`, `yang`), so the original chase code runs right after it and finds nothing to chase. The local player (client owned, as in the original) and the host's own zombies never get one: movement of the local player is instant, nothing is delayed.
* `?interp=0` turns it off (original behaviour).

### State messages (compact encoding) and send rate
`setzumbistuff`, `setposstuff` and `updateposition` sent with mode `Others` are encoded as `STATE` instead of an RPC (no method name, no argument tags): `u8 kind, i64 view` then kind 1 (zombie) `i16 yaw, 3 x f32`, kind 2 (player) `i16 yaw, i16 head, 3 x f32 position, 3 x f32 (exposi, exposiback, lean)`, kind 3 `3 x f32`. That is 24 / 38 / 22 bytes against 47 / 65 / 40 as RPC messages. The receiver rebuilds the original RPC arguments and calls the same methods, so the scripts cannot tell. The relay forwards `STATE` to everyone except the sender, unbuffered, and drops bodies with a wrong length. `?compact=0` sends plain RPCs.
The host raises `sc_player.sendrate` / `sc_zumbi.sendrate` of every object it instantiates to 30 (`?rate=N`, `?legacy=1` leaves the original 10): the scripts' counter is per frame, so this gives about 20 updates per second at 60 fps and one per frame below 30 fps. Only the network update rate changes, nothing in the game rules.

### Batching
Messages produced in one game frame were already sent as one WebSocket frame in version 1 (`ZbNet.Queue` / `FlushOut` in `LateUpdate`), and the relay already answered with one frame per recipient per incoming frame (`room.js` `webSocketMessage`: unpack, route, regroup). What version 2 adds: the relay prepends the sender's `TIME`, the frame stays in order, and `server/test/relay.test.mjs` now tests it (one frame per recipient, order, 400 messages in one frame, frame without clock). Waiting to merge frames of several senders would add latency and was not done.

### Round trip to the host
`ECHO` goes through the relay to the host and straight back (client to host once per second, host to every client once per second); the answer is produced by the host's game loop, so it contains the host's frame delay, which is what the player's actions also see. The old `PING` only measures the relay (still used for `Network.GetAveragePing`).

### Latency test mode
`?netsim=RTT,JITTER` on the page URL (e.g. `?netsim=120,30`), implemented in `ZbNet.jslib`: every message this browser sends or receives is delayed by `RTT/2` plus a uniform random `+-JITTER/2`, in order like TCP (a late message holds back those behind it). Add it to the pages that should be "far away"; a client and a host that both use `netsim=60,20` talk with about 120 ms round trip (the path crosses two delayed legs each way). Other test switches: `?legacy=1` (no interpolation, no compact state, original send rate; the same build as the "before" baseline, apart from the clock stamps and echo pings that stay on), `?interp=0`, `?compact=0`, `?rate=N`, `?delay=MS`, `?stats=1`.

### Instant feedback for shooting
Nothing had to change, it already is shooter-first in the original design (checked in `sc_player` / `sc_shot`): the shooter instantiates the bullet and the muzzle flash locally (`Network.Instantiate` creates the local object before anything goes out), plays the sound and the animation locally, and the bullet's own raycast runs on the shooter's machine (`NetView().isMine`): it applies the damage to the zombie it sees (`sc_life.hurtme` locally and the `hurtme` RPC to the others), shows the hit marker (`add_hitmarker`) and spawns the impact particles, all in the frame of the hit. So hit detection is decided by the shooter against what the shooter sees, not by the host; with interpolation that is the zombie ~100 ms behind the host's truth (the original chase was 150 to 250 ms behind). The e2e test checks that the shooter has its own bullets within 80 ms even with 120 ms of netsim.

## Data channel lane (phase 2, WebRTC)

Design and decisions: `docs/design/PHASE2-WEBRTC.md` (this is its steps 1 to 6). Cost rule: **$0**, so only free public STUN servers
(`stun:stun.cloudflare.com:3478`, `stun:stun.l.google.com:19302`), no TURN, no paid Cloudflare Realtime. A peer that cannot connect directly simply stays on the WebSocket relay, which is exactly what it did before.

```
host browser                                client browser
 ZbNet (API unchanged)                      ZbNet (API unchanged)
  | WS binary: everything (as before) <-- Room DO --> WS binary: everything
  | WS text:   signaling JSON         (relay + signaling)  WS text: signaling JSON
  +==== RTCDataChannel "zb-fast" (negotiated id 1, unordered, maxRetransmits 0) ====+
        carries ONLY host->client S_TIME + S_STATE frames and echo probes
```

* **What moves:** host to client `STATE` (zombies, the host's avatar, host-owned objects) and the end to end echo probes. RPC, INST, DESTROY, KICK, LISTING, PING, WELCOME and the buffered replay stay on the WebSocket, unchanged. Client to host state (`C_STATE`) also stays on the WebSocket in this release (that is "2b").
* **Framing:** the bytes are the same as the relay would send (`u16 len + body`, opcodes `S_TIME 0x8b`, `S_STATE 0x8d`, `S_ECHO 0x8c`), chunked at about 1100 bytes on message boundaries, every chunk led by its own `S_TIME` (sender clock of the moment the frame's first state was produced). The receiver takes the channel's peer as the sender, whatever the frame claims, and ignores any other opcode.
* **Roles:** the client offers (`createDataChannel('zb-fast', {negotiated: true, id: 1, ordered: false, maxRetransmits: 0})`), the host answers; both in plain JS (`game/Assets/WebGLTemplates/ZumbiBlocks/zbrtc.js`), so signaling and probes work while the Unity loop is not running. Unity only polls (`ZbRtc.cs` + jslib shims, no JS to C# callbacks). Star topology only: clients never learn each other's addresses.
* **Signaling** (JSON text frames, at most 8 KB, on the existing socket; the connect URL gets `&rtc=1`; protocol version stays 2, old pages never send it and never get a text frame):
  relay to peer `{"t":"hello","id":N,"host":bool}` right after WELCOME and `{"t":"sig","from":ID,"gen":G,"k":"offer|answer|ice|bye","sdp":...,"c":...}` (`from` is stamped by the relay);
  peer to relay `{"t":"sig","to":ID,"gen":G,"k":...}` (clients may only target the host; at most 60 per 10 s; target must be a player that speaks `rtc`), `{"t":"dc","up":true|false}` (client: "my channel is healthy / not", host: `{"t":"dc","to":ID,"up":false}` can only clear), `{"t":"stat","r":"ok|timeout|...","c":"host|srflx|...","ms":N}` (logged by the relay as `p2p-stat`, so real NAT success can be counted from the Workers logs).
* **Relay change:** in `C_STATE` the host's state is not forwarded to clients whose flag `dc` is set (flag kept in the socket attachment, so it survives hibernation, cleared on `dc up:false`, host clear, socket close). The flag is set only by the client, only after its channel passed the health check. All other routing is untouched.
* **Host side:** while every connected client has its channel up, the host does not even send its state over the WebSocket (that is what removes messages from the Durable Object). While some client is not on the channel (never connected, blocked, `?p2p=0`, dropped) the host sends state on both: channel peers get it directly, the relay forwards the WebSocket copy to everyone not flagged.
* **Health and fallback:** each side sends a probe every 500 ms (answered from JS). The lane counts as **up** after 3 consecutive good probes (hysteresis) and goes **down** when nothing arrived for 1500 ms; a client that sees it down sends `dc up:false` (the relay resumes fan-out at once) and the host sends state over the WebSocket again; recovery needs the 3 good probes again. Connect timeout 8 s; client retries (new generation) at 10 s and 30 s after join, a lane that had been up and dropped restarts after 2 s; at most 6 attempts, then the session stays on the WebSocket. A channel whose send buffer stays above 64 KB for 2 s is demoted. At most 8 channel peers per host, the rest stay on the relay. Because state is idempotent and latest wins, a switch only ever means a short duplicate window or a short gap (bounded by the 1.5 s watchdog), never a desync. The two paths have different latency, so the per sender clock estimate is reset whenever the lane flips (it keeps its value and re-converges at the usual slow slew) and each lane only feeds the clock while it is the active one. State that arrives over the channel before the WebSocket INST of a fresh object is parked for up to 2 s and delivered when the object exists.
* **Switches (page URL):** `?p2p=0` kill switch (no `rtc=1`, byte-identical to the pre phase 2 behaviour), `?p2p=drop` test hook (this client closes its own channel 12 s after it opened, once), `?p2p=block` test hook (ICE can never connect), `?life=MS` (`maxPacketLifeTime` instead of `maxRetransmits 0`), `?netsim=RTT,JITTER,LOSS` (the channel gets the same delay as the socket plus LOSS % of received data frames; `?netsimp2p=` sets the channel alone). `window.zbrtc.info()` shows the state of the lane (tests), `window.zbrtc.stall(true)` makes it swallow everything like a dead path (tests).
* **Stats (F3 overlay and `StatsDump`):** one `Link` line per peer: `DC` or `WS`, the RTT (average of the game's echo probes, which now run over the channel when it is up), probe loss and send buffer; plus DC in/out KB/s and messages/s and the number of lane flips. `StatsDump` has a `p2p` object with the cumulative counters and the links.
* **Privacy:** WebRTC exposes IP addresses to the other end: the host's browser sees every client's IP and each client sees the host's (the relay's anonymous per room id design no longer hides it from the host). Disclosed on the page and in the README; `?p2p=0` turns it off.
* **Not done (by design, see the design doc):** TURN (costs money; strict NAT / corporate networks stay on the relay), reliable channel for RPCs, client to host state over the channel (2b), ICE restart.

### Measured (local relay, headless Chrome with GPU, host + 1 client walking and shooting, both kept alive, 27 s window)
`server/test/e2e/measure.mjs`, `?p2p=0` (before) against the default (after). The cost metric is the number of WebSocket frames the pages send, which is what the Durable Object receives (what the Free plan quota counts); frames the Durable Object sends are not billed.

| | `?p2p=0` | default (channel up) |
|---|---|---|
| WebSocket frames per second received by the Durable Object (4 runs each) | 57.5 to 59.6 (host 32, client 26) | 35.3 to 42.5 (host 11 to 18, client 25) |
| host WebSocket out | 10.9 KB/s, 422 msg/s | 1.0 KB/s, 30 msg/s (the rest, about 10 KB/s, is on the channel) |
| client WebSocket in | 11.1 KB/s | 1.1 KB/s |
| delay of the rendered host to client movement (zombies / host avatar) | 100 ms / 100 ms | 105 to 115 ms / 105 to 110 ms |
| path error of zombies / host avatar (RMS after best constant delay) | 0.013 to 0.017 m / 0.007 to 0.008 m | 0.017 to 0.031 m / 0.015 to 0.028 m |
| client to host (own avatar, WebSocket in both) | 100 ms, 0.010 m | 100 ms, 0.009 m |

What this does and does not show: it is one machine, so the "network" is loopback and the relay hop costs about 1 ms; a direct channel cannot be faster than that and in Chrome it measured 5 to 15 ms slower (DTLS/SCTP processing), so locally there is **no latency gain, a small loss**; the real gain (no detour through the Cloudflare edge, no TCP head-of-line blocking) can only show on a real network, which these tests cannot reproduce (also not real NAT traversal: all candidates were `host` type on one machine; srflx hole punching, symmetric NAT, corporate firewalls, IPv6 and mobile networks are untested until real players report via the `p2p-stat` log lines). What it does show: the host's state traffic left the relay (host to Durable Object -45 to -65 %, total -30 to -40 % with one client; the saving does not grow with more clients because every client's own upstream still goes through the relay, that is what 2b would fix) and the fallback works. With 5 % simulated channel loss the client extrapolated in roughly 40 % of its frames (657 in the window) but the rendered path error stayed at 0.016 m (interpolation bridges lost chunks).

### Verified (phase 2)

Not covered: a real hibernation cycle (the flag is stored with `serializeAttachment` like the player id).
* `server/test/e2e/e2e.mjs` passes with the channel on (42 checks: channel up host to B and C, state counted on the channel, WebSocket state nearly zero, mixed room with a `?p2p=0` joiner, overlay link status), with `?p2p=0` (35, the old set) and with `NETSIM=60,20` (43). `single.mjs` and `supply.mjs` pass.
* `server/test/e2e/fallback.mjs` (host + B + C `?p2p=drop` + D `?p2p=block`): D never gets a channel and plays on the relay (retries then stops); B's channel is stalled (a dead path with no close event): host state to B is starved for about 1.5 s (the watchdog; zombies hold, then flow again over the relay), no teleports, same zombies as the host afterwards, and after release the lane comes back after 3 good probes; C's channel is closed by the page (`?p2p=drop`, the peers are told): no measurable starvation, it reconnects within seconds. That 1.5 s hold on a silently dead path is the price of the design's watchdog value.

## Getting into a game (phase 3)

Everything here sits around the game: `game/Assets/Scripts/ZbMenu.cs` (new file) plus about ten one-line hooks in `sc_gamecontrol`, `sc_spawner` and `sc_player` (listed in `docs/RECOVERY.md`). Gameplay is unchanged; the only change that touches match flow is the Quick Play auto start, which is limited to rooms that Quick Play creates.

**Nickname.** The original already has a Name field (appearance screen, saved as `ZB_<ver>_prefname`, shown above the mannequin). That nick is used for the player name and for the names of rooms that the game names ("<nick>'s game"). If it is still the default (`player`, or empty on a first run) a nickname screen (state 30) is shown once before create / join / Quick Play / an invite is used: 2-10 letters, digits, space, `_ - .`, not "player". The appearance screen field filters the same characters. Duplicate nicknames are allowed (as in v0.7; nothing keys on names).

**Server list** (state 26). `GET /api/rooms` rows: `code, name, players, max, type, pw, comment, wave, started, ended, age (s), colo, country, quick`. Never the host's lat/lon or the password. The game shows name, Wave ("Lobby" / "Wave N" / "Ended"), Ping, Region (country + Cloudflare colo), Players (`n/max`, the original hard coded `/16`). Full rooms are sorted last, marked FULL and cannot be joined; otherwise the lowest known ping first, then most players. Ping is the round trip of `GET /api/ping/CODE` (browser, edge, the room's Durable Object, back; best of 2), measured for the first 8 rows, at most once per 10 s per room, so it is the path the game traffic takes through the relay. The list refreshes every 10 s while open and keeps the selected row selected. Wave / started / ended come from the host: `ZbMenu.HostTick` sends `C_META` when they change (and at least every 30 s); a room whose host runs an older build shows "Lobby".

**Quick Play** (main menu, first row). `GET /api/quickplay?type=Zumbiblocks <buildversion>` returns up to 3 candidates of the same build, listed, no password, not full, not ended, at least one player, best first: rooms not waiting in the lobby for more than 3 minutes (a lobby room that old is probably abandoned; Quick Play rooms are exempt), then most players, then nearest to the caller (distance computed in the Worker from `request.cf`), then newest. The client re-checks the first candidate with `GET /api/room/CODE` right before connecting (closes the race), then joins it. Nothing fits: it creates a listed room named "<nick>'s game" (comment "Quick Play", 16 players, no password). It never uses the original `OnFailedToConnect` candidate list; only if the connect still fails (the room filled up in between) a hook at the first line of `OnFailedToConnect` runs Quick Play again (twice at most), then creates a room.
*Auto start (Quick Play rooms only).* A normal hosted room keeps the original behaviour: the host presses ENTER. A room created by Quick Play starts by itself: once the first player is in the scene a visible countdown "Match starts in N" runs for 10 s on every peer; when a second player joins it is cut to 5 s. At zero the host sets `sc_matchcontroller.gamestarted = true`, exactly what ENTER does (it only fires while at least one player is spawned, because the original ends a match with nobody in it). ENTER still works during the countdown. The host sends `C_META` with the seconds left once a second and the relay forwards them as `S_COUNTDOWN` to the others.

**Invite links.** The page shows a bar "Room CODE  [invite link]  [Copy invite link]" while the tab is in a room (host or client; `ZbSetRoomUi` in the jslib calls `window.zbSetRoom`). The copy runs from a real click on that DOM button (clipboard API with an `execCommand` fallback). The link is `https://<site>/?room=CODE`, never with a password. Opening it: the game reads `?room=` in its first menu frame (state 32), asks for a nickname first if needed, then `GET /api/room/CODE`: unknown / closed room -> "Room X was not found or is closed", another build -> "This room runs another version of the game", ended -> "This match has already ended", full -> "The room is full" (each with Quick Play / Main menu buttons, nothing is loaded); a password room opens the original password screen (state 28); otherwise it joins like the Direct IP button. The `room` parameter is removed from the address (`history.replaceState`) as soon as it was used so a refresh does not join again. After an automatic join the page shows "Click to play" until the first click (browsers need a click for pointer lock / audio).
`GET /api/room/CODE` -> `{exists, name, type, players, max, pw (boolean), started, ended, wave, quick, full}` or 404 `{exists:false}`; never the password or any address.

**Settings.** Main menu Options > "All settings" (state 33), and in game the pause panel (ESC) Options button, which did nothing in the original, opens the same rows as an overlay: Field of view 60-110 (default 70, applied to the local player's `def_fov` and the camera, zooming still narrows by the gun's `add_fov`), Sensitivity and Volume (the original values `ZB_<ver>_sense` / `_sound`, saved by the original `save()`), Graphics Low / Medium / High, Invert vertical look. New keys `ZBX_fov`, `ZBX_invy`, `ZBX_quality` (own keys, not wiped by a save version bump); every change calls `PlayerPrefs.Save()` (sliders: when the mouse is released). Graphics maps to the project's existing QualitySettings levels: Low = 1 "Fast", Medium = 3 "Good" (what the WebGL build uses, the default: an untouched profile never calls `QualitySettings`), High = 4 "Beautiful". Invert Y changes the single read of `Mouse Y` that aims (`sc_player`, `headang`). The existing autoaim / autoreload toggles stay on the original Controls screen.

## Resilience (phase 4)

Design: `docs/design/PHASE3-4-MATCHMAKING-RESILIENCE.md`. What shipped and how it differs from the design is listed here.

### Limits (step 1)
Per IP and per minute, all in memory or in the Lobby DO (nothing paid): `/api/rooms|room|quickplay` 240 (counted in the Worker isolate, so a refused request costs no Durable Object call), `/api/ping` 600 (an open server list probes up to 8 rows twice per 10 s, about 100 a minute per player), new rooms 20/min and 200/hour, first joins 90/min, rejoins 180/min (a Wi-Fi blip makes a whole NAT retry at once, so rejoins have their own bucket). A refused WebSocket upgrade is answered with a normal socket that carries `REJECT(6)` and closes (a browser cannot read the status of a failed upgrade); the client retries a resume that gets 6. Per socket: the byte bucket of before plus a message count bucket (host 15000/s, was 3000/s until the zombie backlog (hundreds of zombies at 20 messages/s each over the relay), clients 600/s, burst 2 s; over budget the message is skipped, 100 in a row close the socket). Frame 64 KB, message 8 KB, 512 messages per frame, buffer caps unchanged. Not done: the RPC / INST content validators in shadow mode.

### Desktop-only gate (step 2)
The page template checks the user agent (Android / iPhone / iPad / Mobile ...), iPadOS (Mac user agent with touch points), `userAgentData.mobile` and `(pointer: coarse)` without any fine pointer; on a match it shows the message and never starts the 100 MB download. A narrow desktop window is not gated. `?desktop=1` skips the check. Test: `server/test/e2e/mobile.mjs` (iPhone, Android phone, iPad, Android tablet, invite link, narrow desktop, `?desktop=1`).

### Reconnect (step 3)
* A protocol 3 socket that dies without a clean close code (anything but 1000 / 1001; the page closes with 1000 on Disconnect, a tab close sends 1001) keeps its player in **limbo**: slot reserved (it counts toward capacity and the room list), 20 s for clients, 15 s for the host, persisted so a Durable Object restart keeps it. Joins get a token (16 random bytes, stored in the socket attachment and sent in WELCOME, rotated on every resume) and the same token is kept in `sessionStorage` (`zb.resume`) so a reloaded tab can free its old limbo slot (`stale=`).
* A visible protocol 3 socket that sends nothing for 12 s is treated as dropped too (a dead network does not always close the socket). The check runs on incoming frames (once a second) and in the alarm, no extra alarms. Hidden tabs (C_VIS) are never dropped for silence.
* **Resume**: `ZbSession` logic in `ZbNetSession.cs`. The client reopens the socket with `rejoin=ID.TOKEN&seq=N` (NOT through `StartClient`, which resets everything), the resumed WELCOME does not run `OnConnectedToServer` or `OnPlayerConnected`, backoff 0.4, 0.8, 1.6, 3 s, a "Connection lost - reconnecting N s" overlay, and the game keeps running meanwhile. The relay replays buffered entries with `seq > N` that are not the player's own, plus S_DESTROY for roots destroyed meanwhile (tombstones, 60 s), then SYNC_DONE. Buffer entries have persistent sequence numbers (snapshot format 2, `bufGen`); after a Durable Object restart the counter jumps by 65536 so no number is reused. The relay counts the buffered operations it parsed from each player (INST, buffered RPC, DESTROY, REMOVE_RPCS, DESTROY_PLAYER) and returns the count in the resumed WELCOME; the client re-sends the missing tail from a ring of its last 4096 operations (count based: nothing is applied twice, own echoes are never replayed). `S_INST` is deduplicated by view id.
* The WebRTC lane is left alone by a resume (a data channel does not depend on the socket). The relay's `hello` carries `resumed: true`; the client re-announces its channel as up, or starts a new attempt if it has none.
* Host: same mechanism. Clients see "host connection lost" (host state 1); joins get REJECT(9); requests to the host (`Server` mode RPCs, player-left notices) are queued (300 entries / 128 KB) and delivered on resume. Grace over = the host is gone (below).
* Test knobs, only with `wrangler dev --var ZB_TEST:1`: `grace=`, `tstale=`, `tclaim=` on `/ws/host`, `X-Zb-Test-Ip`.
* Tests: `server/test/relay.test.mjs` (resume replays only what was missed and never own entries, token rotation, tombstones, grace expiry, capacity, v2 unchanged, host away / queue, ...), `server/test/e2e/reconnect.mjs` (socket killed mid game: same id, same money, host never sees a leave, lane back, host drop, 26 s offline falls back to the menu).

### Host leaves (step 4)
* **Level A** (approved by Vito, a deliberate rule change: v0.7 gave clients nothing when the host left): when the host is gone for good (clean leave, tab closed, or its grace ran out) every client banks the match money exactly like the ESC Disconnect does (`money += match money`, saved) and sees "The host left the game. Your money from this match was saved."
* **Level B, claim restart** (no role pointer, `hostId` stays 0): the relay picks a successor (a visible protocol 3 player, lowest relay rtt, lowest id), bumps `epoch`, tells everybody `HOST_STATE 3`, closes their sockets with REJECT(4) and keeps the room (code, password, name, listing). `/api/room/CODE` then answers `hostState: "restarting"`, `restart: {successor, claimOpen, wave}`. The clients show the host-left screen and poll that endpoint (no socket needed): after a 3 s pause the successor claims the room (`/ws/host?claim=CODE.ID.TOKEN`, the token proves it was a player) and starts a fresh host session (state 3, `LoadLevel(1)`); once `hostState` is `ok` with a new `epoch` everybody else joins it through the normal join path (new ids, fresh avatars, match money 0, saved money kept; the wave and the players' items continue, see level B+). If the successor does not claim (or opted out with "Main menu") any remaining player may after 10 s; 45 s without a claim closes the room; a lone host leaving closes it at once. A late claimant gets REJECT(8) and joins the winner instead. Not carried over: the host-side ban list. Level B+ below makes the new match continue the old one (wave, rules, everybody's items).
* **Level B+, continue** (2026-10-10, after playtests: players hated starting over at wave 1): the claim restart above, but the new match continues the old one. `game/Assets/Scripts/ZbCarry.cs`.
  * *Snapshot*: every peer keeps, 4 times a second while in an online match, what it knows locally: the wave (`matchdata.wave`, synced by `syncwave`), match time and zombies killed (`sendstuff`), the room's rules (Timed / Classic waves: `waveleft >= 0`; More / Classic loot: new unbuffered RPC `zbroom(flags)` that the host sends every 2 s, flags 1 timed, 2 more loot), the number of players (spawner objects) and its OWN player: the 10 inventory slots (`sc_player.item / quant / ammo`: item id, rounds in the magazine / count, spare ammo), the selected slot, health (`sc_life.quantia`), revives left (`lifes`) and kills (`sc_spawner.kills`). A downed player (revivable body) keeps the body's inventory; a player out of revives (items dropped on the ground) gets a fresh avatar with the normal loadout. The inventory is owned and updated by the player's own `sc_player` in the original, so none of this needs the host's data.
  * *Freeze*: when the host is gone for good (reason 4, the level A banking) the last snapshot is frozen. Not a new one: by then the session is reset and "mine" would match the departed host's objects. The relay also keeps the last wave of a started match in the restart info (`/api/room/CODE` -> `restart.wave`), used only if the player did not know the wave (joined a moment ago).
  * *New host*: sets the new `sc_matchcontroller` to wave W - 1 with the old match time and kills, and the old room's rules override its own Timed / Loot settings for this match (also for the leaderboard's rules check). It starts the match by itself (no ENTER) once its avatar is in and the expected players are connected (old players minus the host) plus 3 s, or 25 s after its avatar spawned. The original's first wave step then does `wave++` and spawns wave W exactly like a normal wave start: per-wave zombie life / head life / damage / speed, zombie count with the Timed player scaling, the cap, and the 120 s timer from 0. ENTER also works and gives the same result.
  * *Every player* (new host and joiners): when its new avatar spawns, `sc_spawner` (right after the normal loadout is put in, before the avatar's `Start`) calls `ZbCarry.OnSpawn`, which writes the frozen slots, selected slot, health and revives into it and restores the kill count on all peers (new unbuffered RPC `sc_spawner.zbkills`).
  * *On screen*: the host-left screen says "The match continues at wave W with your items." / "You are the new host. Continuing the match in N..."; in the new match "Host left - continuing at wave W" (the new host also sees "waiting for players (n/m)" and the last seconds) until 5 s after the wave started.
  * *Classic rooms continue too* (same wave, Classic rules kept): it is a host-left feature, not a gameplay rule change. One Classic detail is not kept: the original disarms the 120 s timer after a timed-out wave (`canlongwave`); the continued wave starts with it armed, as after a cleared wave.
  * *Not carried (accepted)*: zombies alive (a fresh wave W spawns), ground loot, constructions / barricades, vehicles, the burning belt flare, bleeding, the old host's ban list. Match money is not carried either: level A banks it into the saved money, the new match counts from 0 (no double counting).
  * Tests: `server/test/e2e/hostplus.mjs` (host + 2 clients at wave 3, a client with two extra guns, money, kills and less health; Disconnect: same wave on both, zombie count and per-zombie life of that wave, timer 120 s, match time, items / magazines / spare ammo / selected slot / health / kills back, money banked, the next wave follows; tab close in a Classic waves + Classic loot room with one client whose own settings are Timed / More: same wave, Classic rules, Classic zombie count, items back). Test hooks `DebugGive("")` / `DebugGive("id,quant,ammo")`, `DebugKills("n")`; `DebugDump` has `quant`, `ammo`, `sel`, `lifes`, `kills`, `started`, `min`, `sec` and `carry`.
* **Why not level C** (state preserving migration): the zombies, wave timers, ground item quantities, construction durability and vehicles live only in the host's scripts and are not in the relay's buffer. Taking them over needs the adopt pass of ~15 scripts that decide their role in `Start()` (`sc_zumbi`, `sc_findmyarea`, `sc_barbwire`, ...), a snapshot stream, an owner remap in the shim, and a multi-browser soak; constructions and vehicles are not even audited. Done blind it would desync silently, so by the design's own rule ("stop if unsafe") level B is the production behaviour and level C stays out. The relay already reserves the ops (18, 19, 0x90-0x94).
* Tests: `server/test/e2e/host.mjs` (Disconnect with two clients and money, tab close with one client, dead connection beyond the grace, successor opts out, nobody left), plus `e2e.mjs` where the last player now takes over.

### Hidden host tab (step 5)
* The host's game runs in its tab; browsers pause or throttle hidden tabs, so everyone else sees a freeze. The page sends C_VIS on `visibilitychange`; the relay broadcasts HOST_STATE 2 (also to late joiners, and in `/api/room`); clients show "The host's browser tab is in the background - the game is paused until they come back"; the host's tab title blinks "(!) HOST PAUSED - come back" while hidden and a banner explains on return. A hidden player is never dropped for silence. The JS receive queue of a hidden tab drops lossy frames (state, echo, pong, unbuffered RPC) above 600 queued frames, buffered ones are always kept.
* **Spike result, honest version**: whether Unity 6 WebGL keeps ticking in a hidden tab with `runInBackground = true` could NOT be measured here. Playwright (headless or headed, with focus emulation off, backgrounding flags removed, windows covering each other, minimised window) always reports `visibilityState === "visible"`, so a hidden tab cannot be reproduced in automation. What is known: Chrome stops `requestAnimationFrame` in hidden tabs and clamps timers to 1 Hz (once a minute after 5 minutes hidden), so the expected result is "effectively paused", which is why the design is warn + show "host paused" rather than try to keep it alive. To get numbers, open the game in a real browser with a second tab and read `ZBSTATS` tx frames over 10 s hidden (`unityInstance.SendMessage("ZbNetRunner","StatsDump","")` works in a hidden tab). `server/test/e2e/hidden.mjs` therefore simulates the visibility change (property + event) and covers the whole signalling path.

### Playtest features (not in v0.7)
* **Timed waves** (default, host option on the create-server screen in place of the ignored NAT toggle; Quick Play always Timed): `sc_matchcontroller` arms its 120 s "long wave" timer for every wave. The original starts the next wave when 3 or fewer zombies are left or after 120 s, but only arms the timer if the previous wave was cleared, so after one timed-out wave only killing works again. 120 s is the original's own constant (there is no per-wave timing data); the "all dead" threshold stays the original's 3. Classic keeps the original code path exactly. The host writes `matchdata.waveleft`, sent twice a second as the RPC `syncwavetimer` (so late joiners and resumed players have it within half a second).
* **HUD**: `sc_matchdata.OnGUI` draws "Wave N   m:ss" and "Next wave in m:ss" in the original style and font.
* **Teammates' health** (`ZbTeam.cs`): every player sends its own life (0-100) twice a second (`synchealth`, unbuffered); the roster is the players' spawner objects. A list (name, bar, number) at the left edge and a small bar + name above teammates' heads when on screen; "down" when the avatar is gone, removed when the player leaves. Health from a player that never reported falls back to the local copy of its `sc_life`.
* **Zombies per wave scale with the players** (Timed waves only; Classic unchanged): zombies spawned = round((15 + wave - 1) x (1 + 0.5 x (players - 1))). Per-zombie hp / damage / speed per wave stay the original's. "Players" = humans connected to the match (`ZbNet.remoteCount + 1`; the matchcontroller's own `spawners` counter counts the host twice). Wave 1: 1 player 15, 2 players 22-23, 3 players 30, 4 players 38.
* **Zombie backlog, no "max alive" drop** (Timed waves only): the original spawns a wave's zombies only while fewer than 50 are alive and silently drops the rest. Timed never drops one: what cannot spawn now goes into the host's backlog (`sc_matchcontroller.zbacklog`, the wave number of each zombie, oldest first) and spawns 4 per second (`ZbMenu.ZBACKLOG_RATE`, random zombie spawn point each) as soon as there is room, with the stats of the wave it belongs to (`spawnzombie(wave)`, the original spawn code). The backlog carries over into the next waves; a new wave's zombies queue behind it. A wave only counts as cleared (the original's "3 or fewer left") when alive + queued <= 3; the 120 s timer runs as before. Lost like the zombies alive when the host leaves (level B+).
  * **Crash-guard ceiling** `ZbMenu.ZOMBIE_CEILING` = **300** alive (was 80), the same for any player count. **Frame rate guard** (host): when the host's smoothed fps stays below 25 for 3 s, no more zombies spawn (wave starts queue theirs too) until it is back at 30+ for 2 s; nothing is lost. The guard never holds back zombies while fewer than 50 (the original cap) are alive, so a slow PC still gets at least the original game. The guard sees only the host's fps; the ceiling covers the clients.
  * **HUD** (Timed): "Next wave in 1:23   Zombies 64 (+20)" = alive (+ queued). The host sends both twice a second with the wave timer (RPC `synczombies`, unbuffered).
  * **Measured** (`server/test/e2e/fps.mjs`: host A and client B, each its own headless Chrome with GPU on one MacBook (so they share the GPU / CPU, pessimistic), ceiling lifted with `DebugZmax`, guard off, players healed, zombies crowd around them; fps averaged over 6 s, traffic over the same window):

## Relay details (server/src)

* `index.js`: routes `/api/rooms`, `/api/room/:code`, `/api/quickplay`, `/api/ping/:code`, `/ws/host`, `/ws/room/:code`, serves the Unity build from static assets (see Deploy in the README). It also copies the host's `colo` / `country` / `lat` / `lon` (from `request.cf`) into the room at creation; the client cannot set them.
* `room.js`: one SQLite-backed Durable Object per room using the WebSocket Hibernation API. Players are recovered from the sockets' attachments after hibernation; the buffer is snapshotted to storage every 25 s when dirty (and re-read when the object wakes); room metadata is persisted. An alarm every 25 s heartbeats the lobby entry and closes rooms whose host socket is gone.
* `lobby.js`: one Durable Object (`idFromName("lobby")`) with the room list. Entries expire 75 s after the last heartbeat. Only rooms whose host chose "Show in server list" appear. `list()` strips lat/lon, `quickplay(type, lat, lon)` ranks candidates (see above).
* `room.js` also has the read-only RPC methods `info()` (behind `/api/room/:code`, never creates storage) and `ping()`.
* Authorisation is minimal by design: the sender id is stamped by the relay (clients cannot impersonate), clients can only create objects with their own view-id range, only the host can kick / list / act for other players.
* Limits: 64 KB per frame, 8 KB per message, 512 messages per frame, per connection token bucket (host 1 MB/s, clients 96 KB/s, 100 consecutive violations close the socket), 20000 buffered entries / 4 MB per room, 16 players, 250 joiners per room lifetime; per IP request limits, see "Limits (step 1)" under Resilience.

## Known limitations

* Phase 3: the pause-panel settings overlay and the menu use the original's IMGUI look; sliders have no visible track (the original skin has none either). Quick Play ranking is by player count / distance, there is no per-player latency probe beyond the list's relay ping. Phones and tablets are gated (a message instead of the game) until phase 5 touch controls.
* The host is authoritative and runs the zombie AI, so the host's browser tab must stay visible (browsers throttle background tabs; the others see "host paused") and the host's connection decides the game's quality. Mid-match host migration (level C) does not exist; when the host leaves, a remaining player becomes the host of the same room and the match continues at the same wave with everybody's items (level B+), but zombies alive, ground loot, constructions and vehicles are lost.
* Latency: every message takes browser -> Cloudflare edge -> browser. Fine for friends in one region, noticeable across continents. One Durable Object lives in one location (near the first player).
* WebSocket (TCP) instead of RakNet (UDP): a lost packet stalls the stream instead of being skipped (interpolation hides short stalls, a long one shows as a freeze, then a catch-up). Host to client state now travels over an unreliable WebRTC data channel when one can be established (see "Data channel lane"), client to host and everything else still over the WebSocket. Positions are sent at about 20 Hz (the game's own counter with `sendrate` 30), see the Feel layer.
* Vehicles, bags, items and projectiles still use the original chase on 10 Hz `updateposition` (compact now, not interpolated yet).
* Interpolation delay is at least 100 ms: other players are shown 100 to 150 ms in the past (the original was 150 to 250 ms). Hits are decided by the shooter on what the shooter sees.
* Clients are trusted as in the original (any client can send any RPC to any view). Not a hardened anti-cheat design.
* No profanity filter on room names (the nickname is filtered to letters, digits, space and `_ - .`).
* No NAT / port settings: the menu still shows them but they are ignored.
* `Network.Instantiate` calls with a prefab that is not in the prefab table are logged and not replicated.
* Zombie `Start` RPCs `asktheanimation` to the server before the animation reference exists; this logs one `NullReferenceException` per zombie on the host. The call came from the original (the logged exception is harmless) and is kept as is.
